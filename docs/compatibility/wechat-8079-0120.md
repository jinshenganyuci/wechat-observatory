# WeChat 8.0.79 · Observatory 0.1.20

本版包含发送和回执处理的独立健壮性改动，并让看台展示任务正文及真实处理阶段。后续手机对照确认，此次分钟级息屏等待的主要原因是厂商冻结微信；原版 0.1.18 在开启完全后台行为后也能及时发送，不能把恢复归功于本版改动。0.1.20 整体改动暂不合入主线，见文末的版本对照与范围审查。

## 发送通道

- 微信进程使用唯一、有界的串行发送协调器。WebSocket 接收线程独立处理心跳；重连与 HTTP 回退共享正在执行的任务及结果缓存，不能因为连接断开取消已开始的原生发送。
- 原生发送前的账号强校验保留。发送结果确认绑定准备阶段验证过的账号数据库，不再每 500ms 重复等待主线程解析账号。
- ACK 在原连接内按 1/2/4/8 秒退避重传，重传的是结果，不是消息正文。服务端对完全相同的终态 ACK 幂等确认，不重复发布消息事件。没有待确认任务时不运行 ACK 定时器。
- 服务端用独立、有界的 ACK worker 处理结果，数据库等待不占用 WS 收包线程；presence 写入最长 2 秒，ACK 操作最长 5 秒。暂时的 presence 存储故障不再直接拒绝业务结果。
- 当前任务 65 秒没有确认时关闭连接，保留原有租约。新鲜客户端活动允许直接推送；过期连接仍须探测。连接断开后的缓存结果仍需服务器重新分派该任务才能重放，因此可能等待余下租约时间，不承诺断网立即恢复。
- native 发送结果不确定时不会自动再发送正文；进程内缓存不等同于跨进程持久化的 exactly-once 保证。

## 看台

- 当前安装和在线待命安装优先显示；其他安装折叠为历史记录，不再把旧安装 ID 当成手机数量。离线历史记录不显示切换按钮。
- 网页 SSE 连接与手机在线状态分开；离线优先显示，待发数量不再掩盖离线。
- 发送记录展示收件人、正文、创建时间、等待时间、分派次数及错误，可筛选待处理、失败/未确认、最近记录和当前会话。
- pending 表示等待领取，leased 表示已分派待回执，sent 表示微信本地发送状态已确认，不代表对方已读。租约时间不是预计送达时间；结果未确认时先核对聊天记录，避免重复发送。
- 提交防重复点击，失败保留草稿；成功后展示任务 ID 并切到最近记录。网络超时结果未知时不自动重新提交。
- `GET /api/outbox` 仅管理员可读，必须指定 device 和 owner_wxid；设备管理密码不能读取消息正文。该接口不会领取任务或修改发送状态。

## 更新和诊断

同时升级服务端与同签名 APK（0.1.20，versionCode 21），强行停止并重新打开微信一次。微信私有配置保留；无需打开 Observatory 或开启关联启动。本次无新增数据库迁移。

服务端默认关闭阶段日志。联调时设置 `BRIDGE_OUTBOX_TRACE=true`，可记录 enqueue_committed、lease_committed、ws_written、ack_received、ack_committed 和 ack_replayed。仅包含任务 ID、次数和耗时，不包含消息正文、收件人或凭据。

自动验证覆盖 Go race、真实 MySQL、Android JVM、桌面/移动端交互及构建检查。手机息屏、系统冻结和网络断开条件仍需实测；WebSocket 本身不能让被系统暂停的线程继续执行。

## 0.1.20 手机实测：厂商冻结与关闭连接

同日安装 0.1.20 后，样本 04 在 13:13:50 入队，13:16:36 才首次领取并确认发送，等待约 166 秒，仍只分派一次。此次长等待也发生在领取之前，不能归因为 60 秒租约重试。领取后走 HTTP 回退完成。

普通 USB 调试、不使用 root，进一步定位到实际联调的是 user 999 的微信分身。13:24:36 的系统日志显示：

- `OplusHansManager` 在 `StrictMode-1|LcdOff` 场景冻结该微信 UID，包含模块所在的微信主进程。
- 紧接着 `OAppNetControlService` 对同一 UID / 主进程记录 `Close socket`，原因是 `Proc bg(IMMEDIATELY)`，执行成功。
- 13:26:49 和 13:27:15 读取该 UID 的 cgroup：`cgroup.freeze=1`，`cgroup.events` 中 `frozen=1`。其子进程的 `cgroup.freeze=0`，但实际继承父层冻结状态，`frozen=1`。只检查进程自身的开关会漏报。
- 同时手机处于 USB 充电、息屏、普通 Doze 未启用状态，模块此前已报告 `batteryExempt=true`。AOSP 省电白名单和最近任务锁定没有阻止这次厂商冻结。
- 样本 05 于 13:26:18 入队，在上述冻结采样时仍为 `pending`、`attempt_count=0`。13:28:10 模块记录亮屏恢复，同秒首次领取，13:28:11 确认发送，等待约 113 秒。

这些证据确认本次息屏样本受到厂商冻结和断网影响。进程存在不代表线程可以运行；WebSocket 心跳、重连和 HTTP 回退都无法在整个进程被冻结时执行。

用户随后确认在约 13:28 查看设置时**新开启**微信的“完全后台行为”，并非此前一直开启。之后普通 ADB 采样显示 UID `frozen=0`，手机再次息屏。以下对照均只发文件传输助手，使用 WebSocket，且只分派一次：

此对照支持先对微信（尤其分身）放行厂商的后台运行限制，不要求 Observatory 常驻或关联启动，也不默认关闭全局冻结。无需 root 即可读取上述冻结证据。结论限于这台手机、当前局域网和这次六分钟窗口，不代表已验证整夜待机、跨网络切换或所有厂商系统。

## 原版 0.1.18 对照与修改范围审查

使用原始 `baed180370d8d9147d461cccbaeb0b81b54ade28` 同提交的 APK（versionCode 19）和后端，未为对照加入新发送代码。同签名调试 APK 通过 ADB 保留数据降级，重启实际微信分身；配置、安装 ID 与会话分配代码和 0.1.20 相同。测试数据库没有结构差异，无需清表或降级迁移。手机已重新注册为 0.1.18，账号代次正常递增。

两版在各自六分钟窗口中，三条间隔消息均约 1 秒确认。对本次问题，可以直接使用原版 0.1.18；这不是对所有异常链路或整夜待机的保证，也未单独实测相同权限下的 0.1.19。

源码审查区分以下范围，不能以“修复此次冻结”为理由全包合入：

- **0.1.19 的独立缺陷修复**：身份查询原先无超时、心跳同步等待主线程、实际 Pong 未更新安装在线状态。这些有源码及回归证据，但并非本次手机冻结的实证原因。
- **0.1.19 应收窄的恢复策略**：亮屏和解锁都无条件关闭当前连接；连续事件可能在五秒后再关闭刚建立的健康连接。应避免健康连接被无条件重置。
- **0.1.20 的独立发送改造**：收包与原生发送隔离、并发帧写入保护、进行中任务去重存在独立技术理由。ACK 重试、额外数据库 worker 和期限属于更广的可靠性设计，不能通过本次正常发送对照证明其必要性，应单独评审。
- **0.1.20 应收回的优化**：新任务通知从强制探活改为接受 30 秒内旧活动，可能向刚冻结的连接提前租赁任务。恢复通知前探活只增加一个往返；该建议不声称消除原有周期拉取的全部竞态窗口。
- **可独立保留的用户需求**：历史安装折叠、消息正文、创建时间和处理阶段展示。基于 0.1.18 只需新增只读任务查询及前端展示，不依赖 Android 改动或 ACK/连接状态机扩展，也不应捎带新的禁发判定。

以上对照结束时，手机与本机测试后端保留原版 0.1.18，0.1.20 构建产物保留用于比较，整包 PR 未合并。后续按此审查收敛为 [0.1.21 精简版](wechat-8079-0121.md)。
